# 11. SQL로 구현한 카드 IFRS9 ECL 마트 + Stage 이동·PD 캘리브레이션 분석

## 프로젝트 개요
카드 포트폴리오(대만 카드사 3만 명)를 SQLite 기반 데이터 마트로 구축하고, IFRS9 기대신용손실(ECL)
산출 전 과정(Stage 판정 → EAD → ECL → 시나리오 민감도 → 집중도)을 SQL로 구현한 프로젝트입니다.
PD는 파이썬 모델이 산출하고, 충당금 계산과 모니터링은 SQL 마트가 맡는 실무 역할 분담을 재현했습니다.
또한 09번 모델검증에서 발견한 PD 캘리브레이션 문제가 충당금에 미치는 영향을 정량화하고,
Isotonic 보정으로 해소되는지 검증했습니다.

## 분석 배경 및 목적
- 카드사 신용리스크 실무에서 모델(PD)은 파이썬·SAS로 산출하고, 충당금 계산·집계·모니터링은 데이터 마트의
  SQL이 담당하는 경우가 많습니다. 본 분석은 이 구조를 단일 노트북에서 재현해, SQL로 업무 계산 로직을
  구현하는 역량을 보여주는 데 목적을 두었습니다.
- 09-model-validation에서 XGBoost(클래스 가중치 적용) PD가 실제 부실률보다 부풀려진다는 점을 확인했습니다.
  이번에는 그 오차가 충당금 금액으로 얼마나 번지는지, 확률 보정으로 해소되는지 확인했습니다.

## 데이터
- Kaggle "Default of Credit Card Clients Dataset"(UCI 원본): 30,000명, 6개월 월별 연체상태·청구액·결제액,
  다음 달 결제불이행 여부(부실률 22.12%)
- SQLite 마트 테이블: `customers`, `accounts`, `monthly_snapshot`(고객×월 18만 행), `outcomes`,
  `pd_scores`, `ecl_params`(LGD·CCF·할인율 시나리오 파라미터), 뷰(`v_customer_stage`, `v_stage_monthly`,
  `v_ecl`, `v_ecl_all`)

## 방법론
1. **PD 산출(파이썬)**: 연체·결제행동 파생변수로 로지스틱 회귀와 XGBoost(scale_pos_weight 적용)를
   5-fold 교차검증(out-of-fold)으로 학습해 전 고객의 PD 산출, 평균 PD·AUC·캘리브레이션 비교
2. **마트 구축(SQL)**: PRIMARY KEY를 갖춘 정규화 테이블 설계, UNION ALL로 월별 이력 적재, 품질 점검
   (코드 분포, 음수 청구액, 한도 초과, 키 무결성, PD 범위)
3. **Stage 판정(SQL)**: Stage 3 = 최근월 90일 이상 연체 / Stage 2 = 30일 이상 연체 또는 최근 6개월 내
   연체 이력(SICR 대용) / Stage 1 = 그 외
4. **EAD·ECL(SQL)**: EAD = 사용잔액 + CCF × 미사용 한도(Stage 3은 CCF 0). Stage 1은 12개월 ECL,
   Stage 2는 3년 전체기간 ECL(연도별 한계 PD 할인), Stage 3은 PD 100%. 가정값은 `ecl_params` 테이블에
   두고 CROSS JOIN으로 시나리오 확장
5. **모니터링(SQL 윈도우 함수)**: `MAX() OVER (ROWS BETWEEN 2 PRECEDING ...)`로 3개월 치유기간 Stage,
   `LAG()`로 Stage 이동 매트릭스, `NTILE`·누적합·`ROW_NUMBER`로 충당금 집중도
6. **PD 확률 보정**: XGBoost 점수에 Isotonic 회귀를 5-fold 교차적합으로 적용, 세 PD의 ECL 비교

## 시사점
- **순위 변별력이 좋은 모델과 충당금에 쓸 수 있는 모델은 다를 수 있습니다.** XGBoost(가중치)는 AUC가
  가장 높았지만 PD가 실제의 1.9배로 부풀려져, 그대로 쓰면 ECL이 67.1%(358.6) 과대적립됩니다. 이 오차는
  LGD·CCF를 동시에 악화시킨 스트레스 시나리오(+45.2%)보다 큽니다. 과대적립의 약 67%는 Stage 1에서
  발생하므로, 정상 고객 구간의 PD 정확도가 충당금 정확도의 핵심입니다.
- **Isotonic 확률 보정으로 순위 변별력은 유지하고(AUC 0.776 → 0.774) 과대적립을 약 98% 해소**했습니다
  (+358.6 → -7.4). 보정된 XGBoost는 AUC·Brier·ECE 모두 로지스틱을 소폭 앞서지만, 설명가능성과 관리
  부담까지 포함한 모델 선택은 별도 판단이 필요합니다. 09번 모델검증에서 발견한 문제의 후속 해결에 해당합니다.
- **Stage 2는 EAD의 약 25%이지만 ECL의 약 64%를 차지**합니다. 단계가 오를수록 커버리지가 7% → 41% → 75%로
  급증하는 구조라, Stage 판정 기준이 충당금 규모를 좌우합니다.
- **Stage 판정과 EAD를 함께 봐야 합니다.** ECL 상위 20% 고객은 거의 전부 Stage 2 이상이지만, Stage 2 이상
  고객의 약 4할은 ECL 하위 80%에 있습니다. 연체 이력이 있어도 잔액이 작으면 충당금 기여는 작아, 사후관리
  우선순위는 Stage × EAD 조합으로 정해야 합니다.
- **연체의 관성**: Stage 1의 92.82%는 정상을 유지하고, Stage 2의 83.52%는 그 자리에 머뭅니다. 10번 Roll-rate
  분석에서 확인한 연체 지속성이 Stage 단위에서도 나타났습니다.
- **SQL 설계 관점**: LGD·CCF를 코드가 아닌 파라미터 테이블에 두어, 시나리오 추가가 행 삽입만으로 가능했고
  하나의 뷰로 6개 시나리오 × 2개 Stage 정의를 계산했습니다.

## 한계점
- 데이터의 타깃이 "다음 달 결제불이행"이라 12개월 부도를 관측할 수 없어, PD를 12개월 PD의 대용값으로
  사용했습니다. 부실률 22%도 실제 카드업계 연체율보다 훨씬 높아 충당금 절대금액은 현실과 거리가 있으므로,
  구조와 상대 비교 중심으로 해석해야 합니다.
- LGD(75%), CCF(50%), 할인율(15%), 전체기간(3년)은 데이터에 없는 가정값이며, 민감도로 영향 범위만 제시했습니다.
- SICR을 발급시점 대비 PD 상대 증가로 판단하지 못해 연체 이력으로 대용했습니다. Stage 3은 PD 100%를
  적용해 치유(cure) 가능성을 반영하지 않았습니다(실제로 Stage 3의 약 53%가 다음 달 Stage 2로 내려옴).
- 3개월 치유기간 기준 Stage 이동 매트릭스에서 Stage 3 → 1 회복률 0%는 정의에 따른 구조적 결과이며,
  Stage 2 유지율에도 치유기간 효과가 섞여 있습니다.
- 거시경제 전망정보(forward-looking) 반영과 시점별(PIT/TTC) PD 조정은 다루지 않았습니다. 관측기간이 6개월이라
  Stage 이동은 최대 3번 전이까지만 관찰했습니다.
- Isotonic 보정은 이 표본의 부실률에 맞춘 것으로, 실무에서는 다른 기간 데이터로 재보정하고 PSI·캘리브레이션을
  지속 모니터링해야 합니다.
- SQLite는 경량 DB로 Oracle·PostgreSQL 등 실제 환경과 문법·성능 특성이 일부 다릅니다.
